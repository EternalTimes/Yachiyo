# 许可证与持续开放源码

决策日期：2026-10-31；状态：accepted，见 ADR-002。

## 1. 选择与范围

项目维护者希望未来衍生版本也保持开放源码。Yachiyo 的项目原创代码、配置示例与配套文档采用 GNU Affero General Public License version 3 only，SPDX 标识为 `AGPL-3.0-only`。根目录 [LICENSE](../LICENSE) 保留完整文本；本说明用于执行和理解，不修改许可证条款。

具体版本采用 v3 only，不附加“或任何后续版本”的授权。第三方代码和资源按各自声明的原许可证处理，根目录许可证不覆盖这些例外。

## 2. 源码提供

- 分发受覆盖程序的二进制时，按许可证第 6 条提供对应源码或采用条文允许的其他合规方式；Yachiyo 发布流程优先选择在发布页提供同版本源码与构建材料。
- 按第 13 条，修改后的程序支持远程网络交互时，必须显著向所有相应远程用户提供免费获取该修改版本对应源码的机会，即使没有向他们分发二进制。
- 对应源码包括许可证要求的生成、安装、运行及修改所需源码和相关脚本，具体范围以条文为准。仅提供未修改的上游地址不能代替本次修改版的对应源码。
- 个人自行修改、自行使用，不因此自动产生向全世界公开的义务。商业使用、收费分发及服务收费本身允许；不要求衍生作者必须向本项目提交 PR。

官方条文：[GNU AGPLv3](https://www.gnu.org/licenses/agpl-3.0.html)；官方解释：[GNU FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#UnreleasedModsAGPL)。

## 3. 代理场景的入口

首个可运行版本设计 CLI 许可证 / 源码查询入口，提供与运行版本对应的源码获取信息。远程服务场景另外设计用户能够实际看到的入口，例如服务开通页、管理页面或接入说明中的显著提示；本地 CLI 或仅管理员可见的页面不能自动视为已经通知远程用户。

入口不应篡改代理转发的应用数据或插入任意 HTTPS 响应。未实现前在任务和发布清单明确标记；不得声称已有源码提供机制。

参考：[GNU FAQ 对代理服务的说明](https://www.gnu.org/licenses/gpl-faq.en.html#AGPLProxy)；[GNU 应用许可证指南](https://www.gnu.org/licenses/gpl-howto.en.html)。

## 4. 组合与依赖

复制、修改、翻译和 AI 改写均不能被当作自动消除原版权及许可义务的方法。引入前核对具体文件与固定版本，记录来源、许可、组合方式及再分发要求。

GPLv3 与 AGPLv3 的特定组合按双方第 13 条处理；不能直接把原 GPL 文件改称 AGPL。不能组合的依赖应更换实现或取得额外授权，不能只换根目录声明。

直接链接或深度组合的 GUI / 插件需判断是否构成受覆盖作品；独立进程、HTTP、socket 等机制不自动决定法律边界。仅与代理进行普通网络通信的独立软件不因此当然全部变成 AGPL。项目不能承诺所有名称相近或外围搭配的产品都受本许可证约束。

参考：[GNU 兼容性说明](https://www.gnu.org/licenses/license-compatibility.en.html)；[GNU FAQ 对程序组合的说明](https://www.gnu.org/licenses/gpl-faq.en.html#MereAggregation)。

## 5. 后续执行

新源码增加 SPDX 标记，保留准确版权信息；引入依赖时审查许可；发布核对 LICENSE、第三方声明、对应源码、构建材料和用户源码入口。缺少必要材料时阻断相应发布。

许可证保留商业使用权，不增加“禁止商用”等附加限制。未来如考虑另行许可、许可例外或双重许可，必须先审查全部权利来源及贡献者授权，不能仅凭维护者身份替第三方代码或他人贡献重新授权。
